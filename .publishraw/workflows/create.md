# Create

Select the exact collection and intended item identity/path. Read its current JSON profile, readable guide and repository preferences, then read .publishraw/rules/composition.md, .publishraw/rules/layout.md, .publishraw/rules/media.md and .publishraw/rules/publication.md. An available local collection profile may support drafting before its installation reaches the publishing branch, but record that dependency as a publication blocker rather than claiming the item can publish. Ask when the collection or target item is ambiguous.

Create or resume one operation ID and keep exactly one authoritative file at .publishraw/drafts/<operation-id>.md. Reuse that file for the whole revision; never create a competing draft or reconstruct it from chat while it exists. For a new item, establish the intended collection path and confirm its current absence. Record the raw target baseline, current profile/schema digest, configured target when known and selected local media in the ignored operation record. Do not record approval while drafting.

Before every draft edit, read the current draft (or confirm its absence for the first write), the current collection profile and .publishraw/preferences.md. If the file changed since the prior turn, treat its current bytes as authoritative, show the difference that affects the requested change and apply only the requested revision. Preserve unrelated edits.

Compose supplied material into only supported fields and Markdown body roles. Preserve quotations, explicit wording and deliberate structure by default; a verbatim request overrides stylistic improvement. Put grounded headings, summaries, captions, alt text and other supported suggestions into the file so they are reviewed in context. Do not invent people, places, dates, measurements or attribution. Prefer existing taxonomy. Surface every proposal for new categories or tags in the change summary; add it to the draft only when the current profile supports that field and supplied context grounds the value. Collect missing required facts together instead of guessing them. Do not add unsupported or unused optional fields.

After each assembled revision, invoke the pinned adapter runner's validateItem method with purpose: "draft", the current profilePath and authoritative draft itemPath, the current identity index and media evidence. The operation record supplies the intended public source path used for identity validation. Read the draft and profile immediately before writing the request. Report all actionable diagnostics together and revise only after reading the file again. Existing valid image URLs and local-draft media evidence are permitted while drafting; publishraw-local placeholders cannot pass publication validation. Do not upload, stage, commit, push or create a PR before exact approval.

When the complete draft is valid and ready for review, reread the current operation, draft bytes and profile/schema evidence. Resolve the approved media selection, including each existing URL and each new image's placement; the operation remains the source of new image byte identity and mode. Import prepareDraftApprovalPresentation from the verified release's adapterRunnerEntry and call it with those current inputs. Present the complete Markdown and concise intent summary together with that exact presentation, then ask for explicit publication approval. Do not infer approval from edits, prior consent or a sidecar.

Only after this conductor observes the user's actual explicit approval in the current interaction, reread the same inputs and call recordObservedDraftApproval with the unchanged presentation plus the approval time, evidence reference and scope. Atomically replace only the ignored operation record with the returned contracts-validated record. APPROVAL_PRESENTATION_CHANGED means the reviewed bytes or intent changed between presentation and response: show the new version and obtain renewed approval. Timestamps and transient upload IDs are not editorial intent; text, target, profile/schema, image bytes, placement, layout and mode are.

Before any later execution, reread the operation, draft and profile/schema evidence and call inspectDraftApproval with the actual approval observation. APPROVAL_EVIDENCE_MISSING or APPROVAL_INTENT_CHANGED leaves the operation awaiting approval. Never reconstruct draft text or approval evidence from conversation history or the sidecar. An approved exact result may proceed to the next qualified stage. A normalized-equivalent result preserves editorial identity only after the raw-byte mismatch is inspected and recorded; BOM/CRLF normalization never permits an unexplained overwrite. Any other text, whitespace, code, YAML, target, profile/schema, selected-image, placement, layout or mode change requires renewed approval.

After approval, follow .publishraw/rules/publication.md for current-target validation, the isolated-index commit, intent-before-write and configured direct or pull-request publication with remote-byte verification. PUBLICATION_READY: both configured Git workflows are available for an exactly approved create intent; repository requirements still gate the write or merge.
